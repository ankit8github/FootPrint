# Proposed minimized-evidence-v1 field contract

Written before implementation, 2026-11-25. Fixture-only proposal under ADR-015,
not an amendment/approval of prior ADRs. `phase2-normalized-v1` stays unchanged.
This contract deliberately excludes relationships, classifications, confidence,
explanations and unknown-claim outputs. They are generated by existing engines
offline for provenance checks, never accepted as client-authenticated certainty.
No server recomputation or shared executor is introduced (6C-03).

## Exact field inventory

Every listed field is required, including explicit nullable fields. Every object
forbids extras. Strings are ASCII enum/reference tokens, approved domains or exact
UTC timestamps only. No defaults, truncation, unknown metadata or arbitrary prose.
Arrays retain order; repeated members/features/references are invalid.

| Object | Fields, exact values and bounds |
| --- | --- |
| HTTP envelope | `consent_version`: `fictional-admission-consent-v1`; `consent_epoch`, `expected_revision`: strict integers 1..1000000; `batch`: Batch below. No owner/collection/hash/fixture/synthetic flag/idempotency key. No save occurs so no save-idempotency semantics are invented. |

Six kinds: `site_visit_observed`, `registration_email_detected`,
`transaction_email_detected`, `marketing_email_detected`,
`account_notification_detected`, `unclassified_observation`.

Email Feature: `ACCOUNT_REQUEST`, `ACCOUNT_PREFERENCES_CHANGED`,
`PAID_RECEIPT_CLAIM`, `CANCELLED_BEFORE_PAYMENT_CLAIM`, `UNPAID_INVOICE_CLAIM`,
`NEWSLETTER_CUE`, `QUOTED_CONTEXT`, `UNTRUSTED_INSTRUCTIONS`.
Kinds/features follow the existing engine priority (account request, preferences,
commercial, newsletter); issue observations remain unclassified.

Issue: `OK`, `EMAIL_UNCLASSIFIED`, `DUPLICATE_RECORD`, `INVALID_TIMESTAMP`,
`INVALID_URL`, `INVALID_RECORD`, `INVALID_JSON`, `JSON_LIMIT`, `MALFORMED_MIME`,
`UNSUPPORTED_ENCODING`, `MISSING_SENDER`, `ORIGIN_CONFLICT`, `HTML_ONLY_IGNORED`,
`UNAVAILABLE_HISTORY`, `NOT_APPROVED_SYNTHETIC`, `FILE_LIMIT`, `BATCH_LIMIT`,
`RECORD_LIMIT`, `UNSUPPORTED_FILE`, `PARSER_TIMEOUT`, `PARSER_FAILED`,
`NO_SUPPORTED_FEATURE`, `QUOTED_CONTEXT`, `UNTRUSTED_INSTRUCTIONS`,
`MULTIPLE_COMMERCIAL_REFERENCES`, `FEATURE_LIMIT`. Registry membership further
restricts exact issue/disposition combinations; this is not new classifier logic.

Domain grammar is lowercase registrable label + `.test`, <=68 characters. The
actual finite domain vocabulary comes solely from generated registered batches,
recorded in the manifest; grammar or `.test` alone never admits anything.
Reference strings have exact widths (source 5, event 12, alias 9 or 10).
All limits apply before registry membership. Model schema is separately exported
as `backend/experiments/admission_data/minimized-evidence-v1.schema.json`.

## Canonicalization, generation and review

Canonical bytes: recursive ASCII object keys sorted lexicographically, compact
JSON punctuation, ASCII strings, JSON integers only (no float values), explicit
nulls, no BOM/whitespace/newline. Arrays retain exact engine/source ordering.
Input JSON object key order/insignificant whitespace do not change meaning;
source/row/member/feature/alias order does. Duplicate JSON keys, prototype keys,
nonfinite values and depth >8 fail before Pydantic. Depth counts root container
as 1, each nested object/array adds 1. UTF-8 only, no BOM or surrogate strings.
Registry file trailing newline is storage framing, not part of canonical digest.

Offline generator reads only source IDs/paths/adapters/SHA-256 and scenario source
selections/deletion lists from immutable corpus manifest. It verifies corpus
manifest digest and each selected file against approved raw bytes, then invokes
unchanged `assessSelectedFiles` via the existing Vitest/Node test tooling. This
uses gated parser/normalizer/discovery/context/assessment cores. Expected labels
are never computation inputs. Raw source hashes/paths remain in **offline manifest
only**, never admission payloads/responses. Engine module digests and generated
discovery/assessment output digests provide reproducible provenance, not trust.

Portability refinement after inspection: existing Windows checkouts use CRLF for
many Git text files; Linux CI uses LF. Engine, generator and lock provenance
digests normalize **CRLF to LF only**, as the manifest explicitly records. This
does not rewrite files or normalize raw corpus bytes. The manifest also records
Node/Vite/Vitest/tldts versions, generator version and digest. Source profile
entries project only ID/path/adapter/raw SHA-256, excluding source tags, anchors
and expected annotations. Canonical batch bytes did not change in this refinement.

Permitted profiles are exactly 29 scenario selections, six deletion-survivor
selections (including empty), and each selection in reverse order, enumerated in
the manifest. Existing oracle tests already exercise reversal semantics; this
does not authorize arbitrary permutations, subsets or duplicates. Existing
duplicate scenarios supply duplicate profiles; no new arbitrary copy expansion.
Content-identical envelopes share a content-addressed file; profiles remain
separately traceable. Empty survivor envelope is validation-only, not clear/save.

Regenerate with `node scripts/admission/generate.mjs --write` from frontend;
check with `node scripts/admission/generate.mjs` (default readonly). Review manifest,
all complete canonical bytes, generated digests and full unchanged oracle suite.
Review here is reproducible AI-assisted engineering evidence; independent human
review is pending. Do not call the registry independently human approved.

The server loads bounded local registry files only when explicitly enabled,
verifies their digests/schema/canonical bytes and pinned manifest digest, and
compares server-computed canonical bytes as well as SHA-256. Browser hash/path/
flag claims are forbidden. Corrupt/missing registry fails closed. A SHA-256 is
content addressing, not source authentication or proof events occurred. Future
profiles/version changes require explicit offline regeneration, source/engine
and canonicalization review, a separately reviewed registry pin update, tests
and PR approval; no runtime registration/configuration shortcut.

Review hardening: manifest reads stop at 8 MiB plus one overflow-detection byte;
batch-file reads allow at most 8 MiB canonical content plus its framing newline,
and one overflow-detection byte. Size rejection occurs before an unbounded file
read or decoding. Direct trusted-Python admission calls authenticate and check
CSRF/explicit consent before data work, then copy and strictly revalidate the
**whole** envelope. An instance produced by unvalidated `model_copy` or
`model_construct` is not accepted as proof of contract compliance. These checks
do not change fields, registered bytes/profiles, versions or admission authority.

Replay is intentionally permitted only as repeated validation of the same batch
under current explicit fictional consent/epoch/revision/session. Nothing is
stored or consumed, no receipt confers authority, no idempotent save is implied.
Real identity, persistence consent, domain admission, production serialization
and future recomputation remain BLOCKED pending their separate review gates.

Pre-code generation inspection: unchanged history normalizer emits six fractional
UTC digits while email parsing emits three. Preserve **exactly three or six**
fractional digits rather than silently rewriting engine timestamps; the timestamp
table's three-digit example includes this six-digit union. The first generation
produced 70 traceable profiles and 32 distinct complete batches, maximum 1977
canonical bytes. No unresolved commercial aliases required a widened domain rule.
